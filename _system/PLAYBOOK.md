# Playbook: adding a day

Eleven steps, in order, plus step 6b for the things and step 7b for the ledgers. Each ends with a check. Field rules for every record: `_system/schema/claim.md` (schema v2). Privacy rules: `PRIVACY.md`.

## 1. Ingest
Drag the folder with the day's untouched material (slide photos, videos, recordings, raw transcripts, notes, the agenda) onto `ingest.bat` and type the day number. After a dry run and your `Y` it calls `_system/tools/ingest.py`, which copies the files unchanged into `00-raw/dayN/`, makes JPEG previews in `10-sources/dayN/slides-jpg/` and writes `10-sources/dayN/media.yaml` (capture times, video durations, a suggested session per file). Never edit or rename the files in `00-raw/`. If they are already in `00-raw/dayN/`, `python _system/tools/ingest.py 00-raw/dayN --day N` makes only the previews and the index. Drop anything that shows another attendee (a badge, a face) from every later step.
Add the day's sessions to `20-claims/sessions.yaml` from the official agenda: IDs `DN-S01`, `DN-S02`..., times in quotes (`time: "10:00"`), `speaker` as a string or a list, `coverage` as one value or a list (`[transcript, slides]`), `kind` for lightning talks, panels and Q&A, and the pseudo-session `DN-S00` ("Day N, session not recorded").
Check: `python _system/build_kb.py --check` passes, and every agenda slot has a session ID.

## 2. Clean the transcripts against the slides
For each session write `10-sources/dayN/clean/<stem>.md` from the raw transcript:
- Fix speech-to-text errors against the slides: product and feature names, numbers, acronyms, speaker names. Mark anything inaudible `[inaudible]`; do not guess.
- Drop jokes, banter, housekeeping and false starts. Keep every substantive statement and every audience question with its answer.
- Put the speaker's name in front of each turn and number the paragraphs (`14.`), so a claim can point to `T:<stem>:14`.
Check: every number in the clean transcript matches the slide, or the mismatch is noted in the file.

## 3. Extract claims, session by session
Write `20-claims/dayN.yaml` (start from `_system/templates/day.template.yaml`). One idea per claim, paraphrased in plain English; `ev` points to the photo stem or `T:<stem>:<paragraph>`. In sessions with several speakers every `stage` claim gets `who` (a name, `audience` or `unknown`). Audience questions are `who: audience` and their answers carry `rel: [{type: answers, to: <question>}]`. Add `quote` only where the exact wording matters, at most 25 words, taken from the cleaned transcript. Companies shown as bad examples stay unnamed. Anything about your own sites, clients or employer goes to `70-private/`, never into `20-claims/`: a `private: true` claim is still stored in git (see `PRIVACY.md`).
Check: every slide and every substantive passage of the clean transcript maps to at least one claim, and `build_kb.py --check` passes.

## 4. Verify against Google's documentation
For each `slide` and `stage` claim, find the matching Google page. Add it to `sources.yaml` (title = the page's H1, `checked` = today's date) and set `ver`: confirmed, consistent or undocumented. Technical facts are never `n/a`. Add a `docs` claim for what the page says and an `analysis` claim when the event and the docs differ. A third-party article (for example Search Engine Journal) is a source with `kind: press` and a `press` claim; it never makes a claim confirmed or consistent.
Check: no slide or stage claim is left without a deliberate `ver`, and every quote has been compared with the slide or the audio (`quote_checked: true`).

## 5. Link across days
When a claim repeats, extends, contradicts or updates a claim from an earlier day or session, add `rel: [{type: ..., to: D1-C...}]` on the later claim. Add an `analysis` claim only when there is interpretation to add.
Check: `50-maps/across-days.md` (after the next build) lists the links you expect, and every `contradicts` and `updates` link is reflected in the topic summary.

## 6. Synthesise the topics
Give every claim its topics; add a topic to `topics.yaml` only when no existing one fits (kebab-case ID, unique across the file). Update each touched topic's `summary` and `do` list so they reflect all days, list the claims they rest on in `cites`, and start any sentence that rests only on analysis with "Author's view:". Add questions for the new day to `_system/eval/questions.yaml` (next free id).
Check: each summary is still true after reading all of its claims, and every sentence is backed by a cited claim.

## 6b. Review the things (entities)
`20-claims/entities.yaml` lists the things the event talked about (products, features, crawlers, reports, directives, status codes, standards, metrics, concepts, updates, tools), each with its spellings; the build finds them in the public claims by those spellings and never adds a thing by itself. Field rules: the `entities.yaml` section of `_system/schema/claim.md`. After the build in step 8 (run `python _system/build_kb.py` now if you want to do this step first):
- Read the build summary: the mentions per thing, a `NOTE` for any spelling that newly matches more than 20 claims (the drift alarm), and a `WARNING` for a thing no claim mentions or a `pin`/`unpin` that changes nothing.
- Run `git diff 50-maps/entity-index.md`: it shows exactly the new and lost mentions, each with the words that matched. A wrong one is fixed with a longer phrase, a topic scope (`{s: ..., in: [topic ids]}`), `exact: true` for an acronym, or, rarely, `unpin`; a claim that means a thing without writing any of its spellings gets a `pin`.
- Add a thing only when it has 3 or more mentions and a Google page or a requirement behind it. `python _system/tools/entity_candidates.py --out <a folder outside the repository>/entity-candidates.yaml` lists candidates with their counts. Ids are kebab-case, unique across things, topics and areas, and never reused. A factual relation (`uses`, `affects`, `measured-by`, `applies-to`) lists the public claims that name both things; `is-a` and `part-of` need none. No person, company or attendee is ever a thing.
- If a new recording contradicts a factual relation, record it as a claim-level `contradicts` link and update the relation's `claims`.
Check: the build ends with `OK: things:` and no `WARNING` about a thing, and the new mentions in the `entity-index.md` diff are all right; after adding spellings, read the 100-mention precision sample in `entity-index.md` again (fewer than 5 wrong is the bar).

## 7. Keep the kits current
The developer kit (`25-kits/dev-requirements.yaml`, code in `25-kits/snippets/<key>.md`) and the content kit (`25-kits/content.yaml`) are the only source of `60-outputs/dev/`, `60-outputs/content/` and their pages on the web edition. For each new technical claim, update or add a requirement: `id` `DEV-<AREA>-NN` (next free number, never reused), `level` MUST, SHOULD, MAY or AVOID, an imperative `title`, `why`, `how`, a `test` a developer can run, the public `claims` it rests on, and `status`: `documented` needs a Google page key in `docs`; `event-only` says "said at Search Central Live" in `why`. A snippet is a title line, one to three sentences and fenced code with its language (```html); JSON, JSON-LD and XML must parse. In `content.yaml` add facts (a number keeps its scope), myths, quotes (claims with a `quote`, checked ones first; the build labels an unchecked one "wording not yet checked"), angles (a `caution` for every undocumented point) and glossary terms, and retire items a new day contradicts or updates. Give a glossary term its other name in brackets, as in `Crawl rate limit (hostload)`: the web edition's search then treats both names as one. Two terms that differ only in case, accents or punctuation would share an id, and the build refuses them. Name a person only where a cited claim's `who` holds that name (the build checks it); otherwise write "Google" or "a community speaker" (the build checks that an item saying "community speaker" cites a community speaker's slide or stage claim), and "said at the event" where the kit's credit is "a speaker". The build labels an angle point *Partly documented* when it mixes documented claims with event claims the documentation does not back; split the point or keep a caution for its undocumented part.
Check: `python _system/build_kb.py --check` passes, and the build's `OK: kits:` line counts the new day's items.

## 7b. Keep the ledgers current
Three ledgers are built from the kits and the claims by `_system/kits.py`: the **numbers registry** (`50-maps/numbers.md`, `numbers.json`, the web edition's `content/numbers.html`), the **differences ledger** (`50-maps/differences.md`, the developer kit's `differences.md`, `differences.json`, `dev/differences.html`) and the **question bank** (`60-outputs/content/questions.md` and `questions.json`, `question-bank.json`, `content/questions.html`). Only the differences ledger is written by hand, in `25-kits/differences.yaml`; the build adds the rest. In the community edition (`_system/edition.yaml`) the numbers registry and the question bank belong to the full media kit and are not built: there only the differences ledger applies. After the build in step 8:
- **Numbers.** Every fact with `use: stat` in `content.yaml` is in the registry by itself. Read the build's `NOTE: N public claims state a figure that no stat fact cites` and the list at the end of `50-maps/numbers.md`: for each new-day figure worth quoting, add a fact with `use: stat` in step 7, worded with its scope (market, period, basis, comparison: wording rule 9). A figure not worth quoting needs nothing; the list is a reminder, not a to-do.
- **Differences.** Read the day's `undocumented` slide and stage claims (`50-maps/verification-report.md`) and the new `contradicts` and `updates` links (`50-maps/across-days.md`). Where the day says something Google's documentation contradicts, qualifies or does not support, add a row to `differences.yaml`: the next free `DIF-NN` (never reused; keep 10 to 20 rows, and merge rows on the same point before adding a 21st), a `title`, the slide or stage claims in `event`, the docs claims in `docs` or Google page keys in `pages`, an analysis claim in `analysis` that explains the gap (write one in step 4 if there is none), and `follow`: what to do, starting from what the documentation says. Name the case in wording rule 13 of `content.yaml` too. Where a new day settles an existing row, update its `follow` and claims rather than adding a row. The build refuses a row that cites a missing or private claim, an event claim that is not a slide or stage claim, a docs claim that is not a docs claim, or a page that is not a Google source.
- **Questions.** New audience questions (`who: audience`) and their `answers` links come into the question bank by themselves, and so do new things. A question listed as "No answer recorded" needs either an `answers` link (step 5) or nothing, when the recording really holds no answer.
- People ask the base with `ask.bat`, and agents with `python _system/kb_query.py` (see `60-outputs/agent-pack/AGENTS.md`): both read only the rebuilt agent pack, so they answer from the new day once step 8 has run.
Check: the build's `OK: ledgers:` line counts the stat facts, the differences rows and the audience questions, `python _system/build_kb.py --check` passes, and the web edition's three ledger pages show the new day.

## 8. Build
Double-click `rebuild.bat` (or `rebuild.bat dayN`). It runs `_system/build_kb.py` (topic and session pages, maps, the agent pack, the developer and content kits), then the Deep Dive PDFs, then `_system/site/build_site.py` (the web edition in `60-outputs/site/`, which links the PDFs). `build_kb.py` validates everything first and writes nothing when it finds an error; warnings (for example a photo stem with no file in `00-raw/`) do not stop it. After changing the build itself, run `python _system/tests/run_tests.py`.
Check: the build ends with `OK`, the web edition's search finds the new requirements and glossary terms, and the mindmap (`50-maps/mindmap.html`, Day N chip), three topic pages and `50-maps/mention-matrix.md` show the new day.

## 9. Write the day's PDF
Follow `_system/pdf/README.md`: make `_system/pdf/dayN.template.html` with the day's cover details and write the guide from the topic pages, citing claim IDs, then build it with `rebuild.bat dayN`. It writes the Deep Dive edition only (the main edition; `make_pdf.py dayN` with no style follows `_system/theme.yaml`). The classic Art Deco and modern editions are frozen at their v2.4.0 content and are not rebuilt: when a day's template changes, log what the Deep Dive edition now has that they lack (sections and paragraphs with claim IDs, corrections before and after, new claims per session) under that day in `60-outputs/pdf/classic-editions-log.md`. A new day gets no classic edition unless the owner asks for one (`make_pdf.py dayN deco` or `modern` by hand, see `_system/pdf/README.md`). Then run `python _system/brand/make_brand.py --covers` if a Deep Dive cover changed, so the README cover thumbnails show the new guide.
Check: open the Deep Dive PDF; the cover, title, contents page numbers and footer say Day N, and nothing in it contradicts a claim; the classic PDFs are byte-identical to the last release (`git status` does not list them); add the day's row to the table in `60-outputs/pdf/README.md` and update *The three days* in `README.md` (field guides, day page, status), listing the Deep Dive edition first.

## 10. Independent review
Have someone, or an agent, that did not write the day check it: quotes against the transcript, numbers against the slides, that the links open, and that no private material or attendee data reached `30-topics/`, `40-sessions/`, `50-maps/` or `60-outputs/`. Then test an agent on the pack: `python _system/eval/eval_check.py --template > answers.yaml`, give the agent only `60-outputs/agent-pack/`, paste its answers, and run `python _system/eval/eval_check.py answers.yaml --out eval-report.md` (see `_system/eval/README.md`).
Check: every finding is fixed or recorded, every eval question has full citation recall, and every expect and must_not box is ticked.

## 11. Release
Add a `## vX.Y.Z — date` entry at the top of `CHANGELOG.md` (the build reads the version from the first such heading), rebuild, then double-click `save-version.bat`, which commits and tags the version.
Check: `git status` is clean, `git tag` shows the new version, and `60-outputs/agent-pack/INDEX.md` starts with that version and the new "data through" date.
